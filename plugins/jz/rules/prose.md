# Prose

Numbered so a steer can cite one: "prose rule 4". The numbers never move; a retired rule keeps its number and says so.

1. State the fact. No opener, no hedge, no closing summary of what was just said.
2. Report the state as it is now. Never narrate earlier runs, attempts or sessions; what was tried before is a commit, not a sentence.
3. No mannered phrasing: no metaphor, no coined label, no intensifier such as robust, seamless, elegant or powerful, and no word the repository lists under `## Restricted words`.
4. Do not over-compress. Write full sentences; no fragments, no label-colon chains, no arrows standing in for verbs.
5. Write headings in sentence case.
6. Use straight quotes and apostrophes, never curly ones.
7. Never write emoji, dingbats or decorative symbols in code, comments, docs, commits or PR text.
8. Never put model names or AI identifiers in code, comments, docs, commits or PR text. The exceptions are an ADR's Sign-off line and the PR Decisions line that repeats it, which name models by display name, never by version slug, and a co-author trailer the harness supplies on a commit.
9. Use em-dashes sparingly; a comma, a colon or a new sentence usually reads better.
10. Never mention a predecessor or reference repository in prose that lands in the project; name only the project's own files.
11. Never refer to content the text does not contain: a design "set out below" is written below, or the sentence goes.
12. Put commands, paths, error text and output in fenced blocks, never in prose, and never paraphrase output.
13. Say what changed and where it stands. Do not describe the reasoning or the process that got there.
14. Keep code out of prose: at most one file, function or flag per sentence, and describe the rest in words.
